# VOIDEX — устойчивая доступность для всех пользователей (предложение, production не менялся)

Статус: **предложение на согласование.** Ничего из описанного ниже не применено к production, DNS, серверу или аккаунтам.

## 1. Что на самом деле происходит

| Факт | Источник | Уровень уверенности |
|---|---|---|
| С 9 июня 2025 российские провайдеры (Ростелеком, МегаФон, Билайн, МТС, МГТС) обрывают соединения с **Cloudflare, DigitalOcean, Hetzner, OVH** примерно после 16 КБ. Работает и по TCP/TLS, и по QUIC. | Блог Cloudflare, Медиазона, The Record | Подтверждено первоисточником |
| Этот сервер — DigitalOcean (`161.35.135.122`). Затронутый iPhone — Ростелеком (AS12389). Устройство, которое работает, ходит с американского хостинг-ASN (FDCservers), то есть, по всей видимости, через VPN. | Журнал Caddy, ipinfo | Согласуется с гипотезой, не доказано |
| С самого сервера `gate.smsaero.ru` (Россия): TCP проходит, TLS зависает. Это тот же симптом в обратную сторону. | Workflow «status» (дважды) | Подтверждено |
| Снижение MTU (1280) в контейнерах **не помогло** (TLS-проба до `gate.smsaero.ru` до и после: TIMEOUT). Гипотеза «чёрная дыра MTU» не подтвердилась. | Лог деплоя `7c692a8` | Подтверждено |
| Живые замеры из российских сетей получить не удалось: узлы check-host.net были недоступны (все, включая зарубежные). | Эта проверка | Пробел |

Вывод: проблема не в приложении, не в TLS-настройках Caddy и не в конкретном телефоне. Российские операторы режут трафик к иностранным хостингам и CDN по диапазонам адресов. Любое решение, в котором пользователь из России соединяется с адресом DigitalOcean / Cloudflare / Hetzner / OVH, остаётся уязвимым.

## 3. Рекомендуемая архитектура (вариант D)

```
пользователь (РФ) ──► voidex.su (A → российский IP)
                         │  Caddy (Let's Encrypt, тот же Caddyfile)
                         ▼
                   app (тот же Docker-образ) ──► PostgreSQL 16 (том на том же VPS)
```

- Домен `voidex.su` и DNS у Рег.ру **не меняются**; меняется только значение A-записи в момент переключения.
- Тот же стек (`deploy/docker-compose.prod.yml`), те же секреты (`AUTH_ACCESS_SECRET`, `AUTH_TOKEN_PEPPER` переносятся без изменений, иначе слетят сессии и коды), тот же образ.
- Аккаунты и данные: `pg_dump` с DO → `pg_restore` на новый сервер. Refresh-токены лежат в БД, cookie «host-only» на том же домене, поэтому пользователи остаются в системе.
- DO-сервер остаётся неизменным и служит точкой отката первые 7 дней, затем решение (вывести или оставить зашифрованным холодным резервом, согласовав с юристом).

### Что нужно подготовить заранее (иначе миграция сломается)
| Зависимость | Проблема после переезда | Решение |
|---|---|---|
| Деплой через GHCR (`ghcr.io`) | Российский хост может получить троттлинг при `docker pull` | Проверить пробным VPS; запасной путь: `docker save \| ssh … docker load` из GitHub Actions или российский реестр (Yandex / Selectel) |
| SMS Aero | Сейчас `gate.smsaero.org` (Cloudflare) с DO. С российского IP обратная картина | Переключить на `gate.smsaero.ru` (`SMS_AERO_API_BASE`) и добавить **новый IP в белый список** в кабинете SMS Aero |
| otp.com, `api.mymemory.translated.net` | Зарубежные API: возможен троттлинг | Проверить с пробного VPS; отключить перевод (`TRANSLATE_PROVIDER=disabled`) или заменить |
| Let's Encrypt | Должен выпускаться с российского IP (обычно да) | Проверить на пробном домене/поддомене заранее |
| Почта `voidops.ru` | Отдельный домен; затронут только если MX/SPF указывают на IP DO | Проверить DNS-записи этого домена перед переключением |

## 4. План внедрения (каждый шаг с условием остановки)

**Этап 0. Решение (без изменений в системе).** Выбрать провайдера (кандидаты: Timeweb Cloud, Selectel, Рег.ру Cloud, Yandex Cloud; Рег.ру удобен тем, что там уже домен и DNS) и согласовать юридическую часть §5.

**Этап 1. Разведка на пробном VPS (≈ 0,5 дня).** Арендовать VPS на час/сутки, поднять на нём только `curl`-проверки: скачать большой файл (≥ 200 КБ) с `https://voidex.su` (DO) и с GHCR, достучаться до `gate.smsaero.ru`, `api.otp.com`, Let's Encrypt. Стоп, если с российского VPS большие файлы не качаются из нужных мест.

**Этап 2. Стенд (≈ 1 день).** Поднять копию стека на новом VPS **на отдельном поддомене** (`stage.voidex.su`, одна новая A-запись у Рег.ру; требует вашего подтверждения). Восстановить обезличенную копию БД. Прогнать: вход, SSE, загрузку файлов, SMS, e2e-набор (`pnpm --filter @voidex/web test:e2e:prod` с `E2E_*` на стенд), реальные IP и лимиты (§6). Стоп при любом расхождении.

**Этап 3. Подготовка переключения.** Понизить TTL A-записи `voidex.su` до 300 с за 48 часов (сейчас около 3 часов). Подготовить скрипт `final-sync` (остановка записи → `pg_dump` → `pg_restore` → проверка количества строк в ключевых таблицах).

**Этап 4. Переключение (окно 15–30 минут, ночью).** Остановить приложение на DO → финальный дамп → восстановление на новом сервере → запуск → проверка (health, вход существующего пользователя, SSE, SMS) → поменять A-запись на новый IP → наблюдать 1 час.

**Этап 5. Наблюдение 7 дней.** DO работает, но не принимает записи. Монитор из нескольких регионов (§7) без срабатываний.

**Откат.** До конца этапа 5: вернуть A-запись на IP DO (TTL 300 с, около 5 минут), запустить приложение на DO. Нюанс: записи, сделанные на новом сервере после переключения, надо перенести обратно (`pg_dump` с нового → восстановление на DO) либо принять потерю; поэтому решение об откате нужно принимать в первые 1–2 часа, пока объём новых записей мал. Данные DO до переключения остаются нетронутыми.

## 5. Юридический риск (не юридическая консультация)

С 1 июля 2025 ч. 5 ст. 18 152-ФЗ требует, чтобы **первичный сбор, запись и хранение** персональных данных граждан РФ шли в базах, физически находящихся в РФ. VOIDEX собирает телефоны, имена, даты рождения. Текущий основной контур на DO (за пределами РФ) в этом смысле несёт риск: штрафы до 6 млн ₽ (повторно до 18 млн ₽) и блокировка по требованию Роскомнадзора. Российская база это закрывает и одновременно решает доступность. Перед миграцией стоит показать юристу, как организован сбор данных и где лежат резервные копии.

Отдельно: при ограничениях мобильного интернета («белые списки», с 2025–2026) доступны только ресурсы из списка Минцифры, одно из условий которого — вычислительные мощности на территории РФ. Только российский контур вообще может претендовать на такое включение.

## 6. Что проверено и что нужно проверить для любого прокси-варианта

Из кода (`apps/server`): приложение не использует WebSocket; для real-time есть **SSE** (`GET /api/events`, `text/event-stream`) — прокси не должен буферизовать и должен пропускать keep-alive. Cookie сессии: `httpOnly; Secure; SameSite=Strict`, host-only — при том же домене работают без изменений. Лимиты запросов и защита входа считаются по `req.ip`; `TRUST_PROXY=true` доверяет заголовку `X-Forwarded-For`, потому что приложение достижимо только через Caddy. **Если перед Caddy появляется ещё один прокси (Cloudflare или российский relay), Caddy должен брать реальный IP из доверенных заголовков (`trusted_proxies`)**, иначе все пользователи окажутся под одним IP: общий лимит входа заблокирует всех, а в SMS-провайдер уйдёт IP прокси. Это обязательная часть любого варианта A или C и не требуется для D (структура Caddy → app остаётся той же).

Размеры: тело запроса по умолчанию 1 МБ (`bodyLimit`), отдельные лимиты на загрузки. У Cloudflare Free/Pro лимит тела запроса 100 МБ и таймаут ожидания ответа 100 с (код 524) — для SSE нужны периодические сообщения.

## 7. Мониторинг доступности из нескольких регионов

Ключевое: проверка должна **скачивать файл больше 16 КБ**, а не только `/api/health` (маленький ответ проходит даже при троттлинге).

- `deploy/probe/availability-probe.mjs` + `.github/workflows/availability.yml` (в этой ветке, **не влиты**): раз в 15 минут через публичный API Globalping запрашивает `https://voidex.su/api/health` и крупный скрипт сборки из точек в РФ, Германии и США; при ошибке или таймауте падает и открывает issue. Бесплатно, без новых аккаунтов. Не запускался (из рабочей среды нет доступа к api.globalping.io): первый запуск — вручную через «Run workflow».
- Дополнительно (требует регистрации, ≈ бесплатный/недорогой тариф): монитор enterno.io в регионе `ru-msk` на крупный статический файл, UptimeRobot/BetterStack из ЕС и США. Ни один сервис не представляет мобильных операторов, поэтому реальную картину по Ростелекому/МТС даёт только клиентский сигнал: события `client event: boot_failed` в журнале (уже работают) — вывести их счётчик в еженедельную сводку.
- Для оповещений: Telegram-бот или e-mail (нужен ваш выбор канала и токен, их я не создаю).
